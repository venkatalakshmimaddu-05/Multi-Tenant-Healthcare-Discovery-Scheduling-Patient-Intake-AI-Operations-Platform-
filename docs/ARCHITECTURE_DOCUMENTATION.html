AuraCare AI — System Architecture

Autonomous Multi-Tenant Healthcare Access, Clinical Triage & Central Scheduling Platform
Executive Overview: AuraCare AI eliminates healthcare administrative friction and clinical department silos by providing an autonomous, voice-first patient access engine. Patients describe symptoms naturally; the platform performs risk-stratified clinical entity extraction, deterministic red-flag emergency screening, dynamic missing-information discovery, multi-system differential formulation, and atomic EHR appointment booking with verified availability across multiple independent hospital organizations.

2. The 9-Stage Clinical Reasoning & Safety Pipeline

The medical symptom assessment engine enforces a strict 9-stage clinical reasoning process compliant with PRD Section 20 Clinical Safety Guardrails:

StageComponentClinical Function
1Patient InputCaptures patient unstructured natural-language voice or text input, preserving verbatim wording.
2Entity ExtractionExtracts standardized clinical concepts across 9 organ systems without prematurely assigning diagnostic labels.
3Structured StateMaintains persistent state tracking 4-way polarity: PRESENT, NEGATED (e.g. "no fever"), UNCERTAIN, and UNKNOWN.
4Red-Flag ScreeningDeterministic safety layer evaluates ACS, Stroke (FAST), Thunderclap headache, acute GI bleeding, and anaphylaxis prior to routine scheduling. Mandatory 911 / ER refusal.
5Missing-Info DetectionPrioritizes missing information: Emergency risk > Differential discrimination > Care level. Excludes known/negated factors.
6Differential FormulationEvaluates multi-system differentials with expressed uncertainty ("several possibilities such as...").
7Dynamic Follow-UpSelects at most ONE focused follow-up question per turn to avoid cognitive overload.
8Specialty TriageRoutes accurately (Abdominal → Gastroenterology, Ear → ENT, Eye → Ophthalmology, Rash → Dermatology, Joint → Orthopedics).
9Voice ResponseGenerates empathetic, clinical voice response with auditable reasoning_basis without leaking private chain-of-thought.

4. EHR Integration & PRD Section 28 Failure Recovery

To ensure resilient healthcare-system interoperability, all booking operations go through an external EHR broker supporting three deterministic failure recovery strategies:

  • Option A (Transient Timeout): Categorizes network latency or timeouts as retryable; automatically retries using an unqiue idempotencyKey to ensure safe execution without double charging or duplicate slots.
  • Option B (Unknown Outcome): If the network drops during an in-flight booking, the broker executes a query-before-insert against the external EHR. If the record exists, it synchronizes state without creating a duplicate.
  • Option C (Unrecoverable Outage): Upon persistent third-party downtime, the system flags the appointment as RECONCILIATION_REQUIRED, logs an incident report in IntegrationOperation, and immediately dispatches an urgent in-app alert to the hospital administrator for manual resolution.

5. Distributed Concurrency & Double-Booking Prevention

When multiple callers compete for the same doctor slot simultaneously (e.g. Monday 9:00 AM):

  1. Distributed Lock Acquisition: Acquires a temporary lock on lock:doctor:{doctorId}:{slotTimestamp} via Redis / Lock Simulator with an automated TTL.
  2. Two-Phase Verification: Verifies doctor availability in internal database, checks doctor personal blocked slots, and queries the external EHR.
  3. Atomic Transaction Commit: Executes slot creation within an atomic database transaction. Any competing caller receives an immediate, polite voice redirect offering the next closest alternative opening.

6. End-to-End Auditability & Tracing

Every interaction is tagged with an immutable correlationId spanning all system tiers: Voice Transcript → AI Intent Extraction → Capability Execution → EHR Sync → Notification Dispatch. Compliance teams can inspect complete execution traces in the Platform Admin Portal.
